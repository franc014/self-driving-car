Lesson 03 · Road & lanes

Lanes are fractions of the road

Start with the road width. Divide it into equal lanes. Then calculate where each lane starts and where its center is. The lerp function helps us find these positions.

Time
16–20 minutes
Prerequisite
Lesson 02

road.js, util.js, main.js
Mission

Why this matters

Where do we put the car so that it starts in the middle lane? To answer this, we need the road borders and the lane width. This lesson shows how road.js calculates them. It also explains how the camera keeps the moving car on screen. You do not need sine or cosine for this lesson.

In the previous lessons, you learned how the car moves and turns. Now we give it a road. We will find the road borders first, divide the road into lanes, and calculate each lane center. We will use the same example throughout: a road centered at x = 200, with a width of 360 and 3 lanes.

Section 01Find the left and right borders

Look across the road from left to right. The x coordinate tells you the horizontal position: larger x values are farther right. To find both borders, start with the road center and move half the road width in each direction.

The constructor is the code that sets up a new Road object. It receives the center position, the full road width, and the number of lanes.

Run the actual numbers from main.js. The canvas is 400 wide, and the road is 90% of it:

The actual road in this repo width = 400 × 0.9 = 360
left = 200 − 360 / 2 = 20
right = 200 + 360 / 2 = 380

The road extends from x = 20 to x = 380. We call this range an interval, written [20, 380]. These values are world coordinates: the positions stored by the road. The camera changes where we draw the road on screen, not these stored values. Section 06 explains the camera.

Width is the whole road

If you treat width as a half-width, you get left = 200 − 360 = −160 and right = 560. The road still looks centered, but it is twice as wide as intended and both lane formulas are wrong. Read the derivation as “center minus half the width,” never as “center minus the width.”

Section 02Find the lane dividers and lane centers

Divide the road width by the number of lanes: 360 / 3 = 120. Each lane is 120 units wide. A lane divider is the painted line between two lanes. A lane center is the position halfway across a lane.

Lane numbers start at 0. Lane 0 extends from 20 to 140, so its center is 80. Lane 1 extends from 140 to 260, so its center is 200. Lane 2 extends from 260 to 380, so its center is 320.

In the formulas below, i is an index, or position number. For a lane center, it is the lane number. For a boundary, it counts lane widths from the left border. A boundary can be a road border or a lane divider. We will explain lerp in Section 03; first, read the additions and multiplications.

The two formulas that place every vertical line laneWidth = width / laneCount
boundaryi = left + i × laneWidth = lerp(left, right, i / laneCount)
centeri = left + (i + 0.5) × laneWidth = lerp(left, right, (i + 0.5) / laneCount)

To find a boundary, start at the left border and add i lane widths. To find the center of lane i, add another half lane width. This is why the center formula uses i + 0.5.

Why the code and the fraction are the same formula centeri = left + (i + 0.5) × (width / laneCount)
              = left + ((i + 0.5) / laneCount) × (right − left)

Now read getLaneCenter as the second formula written out in code:

In main.js, we create the road before the car. Then new Car(road.getLaneCenter(1), 200, 30, 50) uses lane 1's center as the car's starting x coordinate. This puts the car at x = 200, in the middle lane.

Math.min only limits values that are too large. With 3 lanes, getLaneCenter(99) returns lane 2's center. But getLaneCenter(-1) returns a position outside the road. Use whole-number lane indices from 0 to laneCount − 1.

The drawing loop uses the boundary formula, not the center formula:

A lane divider is not a lane center

With 3 lanes, the first divider is one-third of the way across the road: t = 1/3. The first lane center is only one-sixth of the way across: t = 1/6. Use the center to place the car. Use the divider to draw the line between lanes.

Lane width and line thickness are different

laneWidth in this file means the width of a lane, not the thickness of a line. The line thickness is ctx.lineWidth = 5. The names are close; the quantities are unrelated.

Section 03Use lerp to find a position between two values

Suppose you want the position halfway between the road borders. Start at 20 and add half the road width: 20 + 360 × 0.5 = 200. The lerp function does this calculation for any fraction.

lerp is short for linear interpolation. It takes a start value A, an end value B, and a fraction t. It returns the value that fraction of the way from A to B.

Linear interpolation lerp(A, B, t) = A + (B − A) · t
              = (1 − t) · A + t · B    (a weighted average)

At t = 0, add none of the distance: the result is A. At t = 1, add the full distance: the result is B. At t = 0.5, add half the distance.

The second formula gives the same result. It multiplies each endpoint by a share, then adds the results. This is called a weighted average. You can use the first formula for all the exercises here. See Wikipedia's linear interpolation page for more detail.

lerp(20, 380, t) for the road
t Gap used Result
0 0 20
1/6 60 80
1/3 120 140
1/2 180 200
1 360 380

Why linear is enough here

Across this straight road, each increase of 0.1 in t moves the point by one-tenth of the road width. We only need the two border positions to calculate it. A curved road would need more information about its shape.

Here, lerp calculates an x coordinate. It can also calculate a y coordinate. To find a point partway along a segment, calculate x and y separately:

Use the same fraction for both coordinates point.x = lerp(start.x, end.x, 0.3)
point.y = lerp(start.y, end.y, 0.3)
first lane center = lerp(left, right, (0 + 0.5) / laneCount)

Later, a sensor ray will be a segment from the car to a point farther away. We will calculate where that segment crosses a road border. Intersection math finds the fraction along the ray; lerp then gives the crossing position. You do not need to solve this yet. Radu Mariescu-Istodor's segment intersection lesson explains that next step.

t is a fraction, not a distance

t = 0.5 means halfway across the interval, not half a pixel. At t = 1/3 the point is 140 on this road; change the width and the pixel position changes, but the fraction still means one-third of the way across. The fraction stays meaningful when the width changes; a fixed pixel offset would not.

Outside 0 and 1 is extrapolation

lerp(20, 380, 2) returns 740, past the right edge along the same line. The lane code never uses such values, but sensor and collision code sometimes does. The formula does not care whether the point is inside the segment; only the caller decides that.

  2. Switch to 4 lanes. The edges stay at 20 and 380; only the interior changes. Predict the new lane width and centers: 90 wide, centers at 65, 155, 245, and 335. Dividers sit at 110, 200, and 290.

Changing the width moves both edges symmetrically around x = 200, so an odd lane count keeps its middle lane at 200. Changing the lane count keeps the edges fixed and subdivides the same interval more finely. Those are independent controls on purpose.

Section 05Borders are segments, not just lines

So far, we have used only the borders' x coordinates. To draw a border, we also need its top and bottom points. A segment is a straight piece of line between two endpoints. this.borders stores one segment for each road border.

Why keep endpoints as well as left and right? The future sensor code will test where two segments cross. Endpoints describe both vertical and slanted segments. A curved border could be approximated by several straight segments. The drawing loop could still draw each segment from border[0] to border[1].

The road starts at y = −1000000 and ends at y = 1000000. These are large but finite numbers. The glossary calls this practical infinity: the road is long enough for normal use, but it does have ends.

Why not use JavaScript's Infinity? Some calculations with it produce NaN, which means “not a number.” For example, Infinity − Infinity produces NaN. Finite endpoints avoid this problem in later intersection calculations.

Drawing the borders is where canvas state matters:

setLineDash is part of the canvas's drawing state; it persists across paths and strokes until you change it. The empty array restores solid strokes. If you delete ctx.setLineDash([]), the borders inherit the last dash pattern and come out dashed too. The MDN setLineDash reference states the reset rule directly: an empty array clears the dash list and returns strokes to solid.

Style first, path second, stroke third

beginPath(), moveTo(), and lineTo() describe a path; stroke() paints it with the current style. Changing strokeStyle after stroke() has no effect on what is already painted. The code sets the style once at the top, then changes only the dash pattern between the two groups of lines.

Read each border from top to bottom

border[0] is the top endpoint. border[1] is the bottom endpoint. Reversing them draws the same line. Keep the same order for both borders so the data is easy to read.

Section 06The camera keeps the car in view

The car's stored position changes as it drives. But on screen, we want it to stay near the bottom so we can see the road ahead. The camera does this by shifting the drawing vertically. This shift is called a translation. It does not change the stored positions.

Read the translation as a camera. On screen, the car should stay about 70% of the way down the viewport. The car's world y decreases as it drives up, so the world must be pushed down by the same amount. The formula is:

World y to screen y screenY = worldY + (−car.y + 0.7 × canvas.height)

car.y = 200, height = 800   →   screenY = worldY + 360
car's screen y = 200 + 360 = 560   (70% of 800)
car.y = 150   →   screenY = worldY + 410
car's screen y = 150 + 410 = 560   (unchanged)

When the car moves up 50 world units, the translation grows by 50, so everything else on the road moves down 50 on screen. The car stays pinned at 560. The road appears to scroll past it. There is no horizontal translation in this build, so world x and screen x currently coincide; the car can still steer off the side of the road.

In Lesson 02, rotate(−angle) changed how we drew the car's direction. Here, translate(0, −car.y + …) changes where we draw the road and car. Both change the drawing, not the stored data. See the MDN canvas transformations guide for more detail.

Resizing the canvas resets the context

canvas.height = window.innerHeight runs every frame. Setting a canvas's width or height clears the bitmap and resets the rendering context to its default state, including the transform, stroke styles, and dash list. That is why road.draw() sets lineWidth and strokeStyle every frame instead of once in the constructor. See MDN's HTMLCanvasElement.height.

Stored position and screen position are different

World coordinates are the positions stored by the car and road. Screen coordinates are where they appear on the canvas after the camera shift. In both, y increases downward. If an object appears in the wrong place, first check its stored position. Then check the camera shift.

Section 07Check your understanding

Answer from memory. The feedback appears immediately; the explanation appears after you choose.

Five quick road checks

All questions use width 360 unless stated otherwise.

Q1 With 3 lanes, where is the center of lane 1?

The lane width is 120. Lane 1's center is left + 0.5 × 120 + 1 × 120 = 20 + 60 + 120 = 200. 140 and 260 are dividers; 320 is lane 2's center.

Q2 Which t lands on the first divider with 3 lanes?

Dividers are at i / laneCount; the first is 1/3. 1/6 is the first lane center, 1/2 is the middle lane center, and 2/3 is the second divider.

Q3 What is lerp(20, 380, 0.5)?

lerp(20, 380, 0.5) = 20 + (380 − 20) × 0.5 = 20 + 180 = 200. Half of the 360-wide gap is 180.

Q4 Why are the borders stored as point pairs?

Two endpoints define a segment. A future sensor ray can be tested for a crossing with that segment. The same drawing loop can draw slanted segments, or several straight segments that approximate a curve.

Q5 Why does main.js translate before drawing the road?

The camera translation keeps the car at 70% of the viewport height while the road scrolls past. As car.y decreases, −car.y increases, moving the world down.

Section 08Predict, then inspect

Open index.html in your browser and open the developer console. The car should be in the middle lane at the bottom of the road. Predict each value before you type it.

  1. road.getLaneCenter(0), road.getLaneCenter(1), road.getLaneCenter(2). Predict 20 + 60 + i × 120: 80, 200, 320.
  2. road.laneCount = 4; Predict the lane width and all four centers before the next frame redraws: 90 wide; 65, 155, 245, 335. Where is the car now? It stayed at x = 200, which is a divider in a four-lane road. Set car.x = road.getLaneCenter(1); to put it back in a lane.
  3. road.laneCount = 3; and car.x = road.getLaneCenter(1); to return to the original setup. The car's x is stored separately from the road, so changing the lane count does not move the car by itself.

Challenge: what happens if you change only the width?

Type road.width = 300;. The calculated lane centers change because getLaneCenter reads the current width. But the drawn borders stay at 20 and 380. The constructor calculated left, right, and borders only when it created the road. Changing width does not calculate them again.

The stored values no longer agree: the lane centers use a width of 300, but the drawn road is still 360 wide. To avoid this, create a new Road with the new width, or add a method that updates all these values together. Reload the page after this experiment to restore the original road.

The rule is simple: right − left must equal width. The dividers use the distance between the borders. The lane centers use the stored width. If those distances differ, the dividers and lane centers no longer describe the same lanes.

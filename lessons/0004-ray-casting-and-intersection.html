Lesson 04 · Sensors & vectors

Where a ray meets a border

A sensor casts rays. Each ray is a segment. A hit is the one point shared by two segments — and two fractions, t and u, tell you where.

Time
35–40 minutes
Prerequisite

Mission

Why this matters

How far away is the road edge? The car cannot see; it can only compute. A sensor casts rays and keeps the closest hit. This lesson derives the ray, the fan, and the intersection test that turns two segments into a distance.

In Lesson 03, the road borders became segments. Now we point a ray at them. The question “where does the ray cross the border?” becomes two equations with two unknowns. The solution is getIntersection — and the same function will handle traffic, walls, and any future polygon.

Section 01A sensor is a fan of rays

A real proximity sensor sends out a signal and waits for the echo. The delay gives the distance. The simulation skips the signal and computes the distance directly. The technique is ray casting: from a point, in a direction, find the first thing the line meets.

The Sensor class holds the car and three settings:

The sensor's three settings
Property Meaning Value here
rayCount How many rays are in the fan 8
rayLength How far each ray reaches, in world units 200
raySpread The total angle of the fan, in radians π/2 (90°)

Spread is the whole fan

raySpread is the angle between the first and last ray, not the gap between two neighbours. With 8 rays and a 90° spread, the outer rays sit at +45° and −45° from the car's heading. The gap between adjacent rays is 90° / (8 − 1) ≈ 12.9°, not 45°.

The code comment is wrong

Math.PI / 2 is 90°, not 45°. The trailing comment is stale: it was probably copied from an earlier Math.PI / 4 version. Trust the arithmetic, not the comment. If you want a 45° fan, write Math.PI / 4; if you want the 90° fan this branch actually uses, fix the comment.

The video uses different numbers

Radu's Lecture 3 uses 5 rays, a length of 150, and a 90° spread. This repo uses 8, 200, and 90°. The numbers change the picture, not the mathematics. The lab lets you try both.

A ray is a question: what is the nearest object along this direction? The answer is a point and a distance — or null if nothing is close enough. The sensor's job each frame is to cast the fan, ask every ray, and store the readings for the car's brain to use later.

Section 02A ray is a vector with a start and a length

You already have the direction vector. In car.js, the car moves by (−sin θ, −cos θ) times its speed. The same vector points along the car's nose. A ray at angle θ uses that vector, scaled by the ray's length:

The ray endpoint d = (−sin θ, −cos θ)   (a unit vector along the ray)
end = start + L · d

end.x = start.x − L · sin θ
end.y = start.y − L · cos θ

The fan is an interpolation of angles

The sensor does not store eight separate angles. It sweeps from one side of the fan to the other with lerp. In this branch the loop lives in a private helper called #castRays(), and update(roadBorders) calls it once per frame:

Two details that make the fan correct

+ this.car.angle rotates the whole fan. Without it, every ray points up no matter which way the car faces. The fraction this.rayCount == 1 ? 0.5 : i / (this.rayCount - 1) handles a one-ray sensor: i / 0 would be NaN, so the code chooses the midpoint of the interval instead. fraction = rayCount == 1 ? 0.5 : i / (rayCount − 1)

Why start at +spread/2? Because a positive angle turns left. Index 0 is the leftmost ray, and the loop sweeps to the right. There is no ray at exactly car.angle when the count is even: the two middle rays straddle the heading at ±6.4°. That is a property of 8 rays, not a problem. With 9 rays, the middle ray would point straight ahead.

Radians, not degrees

raySpread is in radians because Math.sin and Math.cos expect radians. π/2 is 90°. To convert: degrees * Math.PI / 180. The lab shows degrees because they are easier to read; it converts before computing.

The ray angle is not the car angle

car.angle is the centre of the fan. Each ray adds its own offset. If the car turns 10° left, every ray turns 10° left with it. The fan is rigid; the car rotates the whole fan.

The vector operations behind the sensor

The code uses a plain {x, y} object for both a point (a location) and a vector (a displacement). The role is decided by how the object is used, not by its type. Four operations do all the work in this lesson:

Vector toolkit used by sensor.js and util.js
Operation Formula Geometric meaning Where it appears
Subtract (B − A) = (B.x − A.x, B.y − A.y) The arrow from A to B r, s, w
Scale L · d = (L · d.x, L · d.y) Same direction, length multiplied by L end = start + L · d
Add A + v = (A.x + v.x, A.y + v.y) Move the point A by the vector v Ray endpoint, P = A + t r
Cross product p × q = p.x · q.y − p.y · q.x Signed area of the parallelogram; zero when parallel tTop, uTop, bottom
Dot product p · q = p.x · q.x + p.y · q.y How much of q points along p Not used here; useful for projections
Why the direction vector has length 1 d = (−sin θ, −cos θ)
|d| = √(sin²θ + cos²θ) = √1 = 1

end = start + L · d   ⇒   |end − start| = L

That last line is the whole reason the code can multiply by rayLength: the sine/cosine pair is already a unit vector. Scaling it changes the length without changing the direction.

The cross product is not 3D magic

p × q takes two 2D vectors and returns one number. Its absolute value is the area of the parallelogram they span; its sign tells you which side q lies on. When the area is zero, the vectors point along the same line, so the intersection equations have no unique solution. That is exactly what bottom == 0 tests in getIntersection.

Section 03A hit is a point on both segments

A segment can be written as a start point plus a fraction of its direction. This is the same lerp from Lesson 03, now applied to both coordinates:

Two parametric segments P(t) = A + t(B − A)   0 ≤ t ≤ 1   (the ray)
Q(u) = C + u(D − C)   0 ≤ u ≤ 1   (the border)

At t = 0 the point is A; at t = 1 it is B. At t = 0.5 it is the midpoint. The same fraction applies to x and y, which is why the point stays on the straight segment.

A hit means the two points are the same point: P(t) = Q(u). Write that equality once for x and once for y:

Two equations, two unknowns A.x + t(B.x − A.x) = C.x + u(D.x − C.x)
A.y + t(B.y − A.y) = C.y + u(D.y − C.y)

Everything else in this lesson is algebra on those two lines. The two fractions answer two different questions:

  • t — how far along the ray is the hit? Distance = t × rayLength.
  • u — how far along the border is the hit? Position = lerp(C, D, u).

Lines cross; segments might not

Two infinite lines cross unless they are parallel. Two segments only cross if the crossing lands inside both finite pieces. That is the whole job of the bounds check: 0 ≤ t ≤ 1 and 0 ≤ u ≤ 1.

t is a fraction, not a distance

t = 0.5 means halfway along the ray, not half a pixel. If the ray length is 100, the distance is 50. If the length changes to 200, the same t = 0.5 means 100. This is the same distinction as Lesson 03's lerp parameter.

Section 04Solve the two equations with a cross product

Name the three vectors in the picture:

The three vectors r = B − A   (the ray's direction)
s = D − C   (the border's direction)
w = C − A   (from the ray's start to the border's start)

The equation A + t r = C + u s becomes t r − u s = w. That is still two scalar equations:

In components t · r.x − u · s.x = w.x
t · r.y − u · s.y = w.y

Eliminate u. Multiply the x equation by s.y and the y equation by s.x, then subtract:

Eliminating u t · r.x · s.y − u · s.x · s.y = w.x · s.y
t · r.y · s.x − u · s.y · s.x = w.y · s.x
────────────────────────────────────────
t (r.x · s.y − r.y · s.x) = w.x · s.y − w.y · s.x

The two u terms cancel because s.x · s.y = s.y · s.x. The left side is t times a single number. The right side is another single number. So:

The two fractions t = (w × s) / (r × s)
u = (w × r) / (r × s)

where  p × q = p.x · q.y − p.y · q.x

The symbol × here is the 2D cross product. It takes two vectors and returns one number, not a vector. That number is the signed area of the parallelogram spanned by the two vectors. It is also called a determinant.

  • Zero means the vectors are parallel, so the two lines never meet at a single point.
  • Positive or negative tells you which side of the first vector the second one lies on.
  • Its size is the area, which is why the formula divides by it: the area cancels out and leaves a fraction.

You can see the same derivation on Wikipedia's line–line intersection page. For the visual meaning of the determinant, watch 3Blue1Brown's “The determinant”.

A worked example

For clean arithmetic, put the car at (320, 200) and fire a ray straight right, 100 units long. (The branch's sensor uses 200, but the numbers are easier to follow at 100.) The right border is the segment from (380, 0) to (380, 400).

The four points and the three vectors
Quantity Value
A — ray start (320, 200)
B — ray end (420, 200)
C — border start (380, 0)
D — border end (380, 400)
r = B − A (100, 0)
s = D − C (0, 400)
w = C − A (60, −200)
Compute the three cross products tTop = w × s = 60 · 400 − (−200) · 0 = 24,000
uTop = w × r = 60 · 0 − (−200) · 100 = 20,000
bottom = r × s = 100 · 400 − 0 · 0 = 40,000

t = 24,000 / 40,000 = 0.6
u = 20,000 / 40,000 = 0.5

Both fractions are inside [0, 1], so the segments really do cross. The hit is:

The hit point P = lerp(A, B, t) = lerp((320, 200), (420, 200), 0.6) = (380, 200)
P = lerp(C, D, u) = lerp((380, 0), (380, 400), 0.5) = (380, 200)

Both routes give the same point. The distance from the car is t × rayLength = 0.6 × 100 = 60, which matches 380 − 320. The ray reaches the border at 60% of its length.

What the bounds reject

The same lines, different fractions
t u Meaning Hit?
0.6 0.5 Inside both segments Yes
1.2 0.5 Past the ray's end No
0.6 1.4 Past the border's end No
−0.2 0.5 Behind the ray's start No
— — bottom = 0: parallel lines No

The infinite lines can cross outside the segments

This is the most common sensor bug. The algebra finds where the infinite lines cross. The bounds check decides whether that crossing is on the piece of line the car actually has. A border behind the car, or a ray that stops just short, still produces a crossing — and must still be rejected.

The expanded terms are the cross products with the vectors substituted. For example, bottom is:

Expand the determinant r × s = (B − A) × (D − C)
      = (B.x − A.x)(D.y − C.y) − (B.y − A.y)(D.x − C.x)

The code writes the same two products in a different order: (D.y−C.y)(B.x−A.x) − (D.x−C.x)(B.y−A.y). Multiplication commutes, so the value is identical. You can do the same expansion for tTop and uTop; the signs work out because both terms flip together.

Why bottom != 0 is enough

Exact parallel lines produce exactly zero in this geometry, and the function returns null. Nearly parallel lines produce a very large t or u, which the bounds check rejects. The code does not need a separate “nearly parallel” branch.

Inclusive bounds matter at corners

t >= 0, not t > 0. A hit exactly at a segment endpoint counts. At a polygon corner, two edges meet at the same point; both can report the same hit. The sensor still works; it just sees the corner twice.

A float comparison to keep in mind

The branch uses e.offset === minOffset when it picks the closest hit. It works because minOffset is copied straight out of the same array, so it is the exact same number. Floating-point equality is fragile in general; if you rewrite this, return the minimum touch directly instead of comparing floats.

Section 06Keep the closest reading

One ray can cross several borders. The sensor only cares about the first one, because everything behind it is hidden. The reading is the touch with the smallest offset:

update(roadBorders) calls #getReading once per ray and stores the results in this.readings. A null reading means “nothing within rayLength”; a reading object is the nearest hit on that ray.

Why is the smallest offset the closest object? Every ray in this sensor has the same rayLength. Distance along a ray is offset × rayLength, so the smallest offset is the smallest distance. If you ever give rays different lengths, compare offset × length instead.

The drawing code uses the reading to split the ray in two. The part from the car to the hit is drawn in the sensor colour; the part beyond the hit is drawn in a second colour. That second colour is the part the sensor cannot see. The fan lab uses the same convention: solid to the hit, dashed beyond.

The same test handles traffic

A future traffic car is a polygon. A polygon is a closed list of points; each pair of consecutive points is an edge, and every edge is a segment. The sensor loops over the edges and calls the same getIntersection:

The closest hit across all the segments wins. A car in front of the border occludes the border. A border in front of the car occludes the car. The sensor does not need a special case for each object type; it only needs the list of segments.

The sensor does not know what it hit

getIntersection returns a point and an offset, not a label. If the car's brain needs to distinguish a border from traffic, the caller can tag each touch with its source before comparing offsets. That is an extension, not a change to the math.

Collision detection is the same idea

To test whether two cars collide, test their polygon edges against each other. Same segments, same function, different caller. Once you can intersect a ray with a border, you can intersect any two polygons.

Section 08Predict, then inspect

Open index.html with the developer console open. The sensor is already wired into the car: car.update(road.borders) moves the car and then calls this.sensor.update(roadBorders) every frame. Use a separate probe sensor in the console so the animation does not overwrite your experiment.

Why the game starts with no readings

main.js places the car at road.getLaneCenter(1) = 200. The borders are at x = 20 and x = 380, so the nearest border is 180 units sideways. Even the outermost ray moves only 200 · sin 45° ≈ 141.4 units sideways. Every reading is null until the car steers closer or turns. That is geometry, not a bug; the lab puts the car in the right lane so the default view has hits.

  1. Check the fan's size. A fresh Sensor has 8 rays, each 200 long, with a 90° spread. probe.rays.length should be 8. If it is not, your constructor settings differ from the branch.
  2. Check that the fan rotates. Point the probe up, record the leftmost ray's endpoint, then turn the probe 45° left. The endpoint should move left. If it does not, the + this.car.angle term is missing.
  3. Test the intersection function directly. Call it with the worked example. The result should be {x: 380, y: 200, offset: 0.6}.
  4. Test a miss and a parallel pair. Shorten the ray so it stops before the border: the result should be null, even though the infinite lines still cross. Then make the ray and the border horizontal: bottom = 0, so the result is also null.

Nine quick sensor checks

All questions use the formulas from this lesson.

Q1 Which vector points along a ray at angle θ?

The car moves by x -= sin(angle) * speed and y -= cos(angle) * speed. The unit direction is therefore (−sin θ, −cos θ). The other options swap the components or the signs.

Q2 In P(t) = A + t(B − A), what does t measure?

t = 0 gives A; t = 1 gives B. The distance from A is t × |B − A|. It is a fraction, not a fixed length.

Q3 For a hit on both segments, t and u must be…

Both bounds are inclusive: 0 ≤ t ≤ 1 and 0 ≤ u ≤ 1. A hit at an endpoint is still a hit; that is why corners work.

Q4 What does bottom = 0 mean?

bottom = r × s. A zero determinant means the two direction vectors are parallel, so the lines never meet at a single point. The function returns null.

Q5 In the worked example, t = 0.6 and u = 0.5. Where is the hit?

lerp((320,200), (420,200), 0.6) = (380,200). The same point is lerp((380,0), (380,400), 0.5).

Q6 Why does the sensor keep the smallest offset?

All rays share the same length, so distance = offset × rayLength. The smallest offset is the smallest distance. Everything behind that hit is occluded.

Q7 Which term rotates the whole fan with the car?

The lerp produces the fan's offset from the heading. Adding this.car.angle turns every ray by the car's rotation. The other settings change the fan's size or range, not its direction.

Q8 Which vector points from the ray's start to the border's start?

C − A is the vector w: “border start minus ray start.” B − A is the ray direction and D − C is the border direction.

Q9 How does the sensor handle a future traffic car?

A car outline is a closed polygon. Each edge is a segment, and the same getIntersection tests every edge. The nearest offset across all edges and borders wins.

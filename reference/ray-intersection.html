Ray casting, vectors, and segment intersection

The compressed version of Lesson 04. Use it when a ray misses, when t and u disagree with the picture, or when you extend the sensor from road borders to traffic polygons.

The one-sentence model

A ray is start + length · direction. A hit is the solution of A + t r = C + u s. The 2D cross product gives t and u; the smallest t is the nearest object.

01The vector toolkit

A point is a location. A vector is a displacement with a length and a direction. In this code both are plain {x, y} objects; the role comes from how you use them.

Every vector operation used by the sensor
Operation Formula Meaning In the code
Add (p + q) = (p.x + q.x, p.y + q.y) Follow p, then q A + t r
Subtract (q − p) = (q.x − p.x, q.y − p.y) The arrow from p to q r, s, w
Scale k · p = (k · p.x, k · p.y) Same direction; length multiplied by k L · d
Length |p| = √(p.x² + p.y²) How long the vector is rayLength after scaling
Dot product p · q = p.x q.x + p.y q.y How much of q points along p Projections; not used here
Cross product p × q = p.x q.y − p.y q.x Signed area; zero when parallel tTop, uTop, bottom
The direction vector from an angle d = (−sin θ, −cos θ)
|d| = √(sin²θ + cos²θ) = 1

end = start + L · d

The two minus signs are the canvas conversion from Lesson 01: the car's 0° points up, and screen y grows down. The sine/cosine pair is a unit vector, so multiplying by L gives exactly length L. Drag the vectors in the lesson's vector lab to see these numbers move.

Dot and cross are different questions

p · q answers “how aligned are these?” and returns a scalar. p × q answers “what area do these span, and which side is q on?” and also returns a scalar. Only the cross product appears in the intersection formula, because the formula needs a determinant in the denominator.

02A ray is a segment with a direction

Ray from the car start = (car.x, car.y)
end = (car.x − L · sin θ, car.y − L · cos θ)

θ = lerp(+spread/2, −spread/2, fraction) + car.angle
fraction = rayCount == 1 ? 0.5 : i / (rayCount − 1)

With an even number of rays there is no ray at exactly the car's heading. The two middle rays straddle it at ±spread / (2(rayCount − 1)). With 3 rays, the middle ray is exact.

03Where two segments meet

Two parametric segments P(t) = A + t(B − A)   0 ≤ t ≤ 1   (ray)
Q(u) = C + u(D − C)   0 ≤ u ≤ 1   (border or polygon edge)

Set P(t) = Q(u). Name three vectors:

The three vectors r = B − A   (ray direction)
s = D − C   (border direction)
w = C − A   (ray start → border start)

Then t r − u s = w. Eliminating u gives the two fractions:

The solution t = (w × s) / (r × s)
u = (w × r) / (r × s)

p × q = p.x · q.y − p.y · q.x

Why the denominator is an area

r × s is the signed area of the parallelogram spanned by the ray and border directions. Dividing by it cancels the “area units” and leaves a fraction. When the area is zero, the directions are parallel and there is no unique crossing.

04Reading the fractions

Every outcome of the intersection test
Condition Meaning Result
bottom = 0 Directions are parallel null
t < 0 Crossing is behind the ray's start null
t > 1 Crossing is beyond the ray's end null
u < 0 or u > 1 Crossing is outside the border's endpoints null
0 ≤ t ≤ 1 and 0 ≤ u ≤ 1 Crossing is inside both segments hit point + offset: t

Distance along the ray is t × |B − A|. In this sensor every ray has the same length, so comparing t is the same as comparing distance. If the lengths differ, compare t × length.

Lines cross; segments might not

The algebra finds where the infinite lines cross. The four bounds decide whether that crossing lies on the finite pieces the car actually has. This is the most common source of “the ray hits something that is not there.”

05Nearest hit and occlusion

update(roadBorders) collects one reading per ray. A reading is either the nearest touch or null when nothing is within range. draw() uses the reading to split the ray: solid to the hit, gray beyond it.

The sensor does not label what it hit

getIntersection returns a point and an offset, not an object type. If the car's brain needs to distinguish a border from traffic, tag each touch at the call site before comparing offsets. The math does not change.

06Any object is a list of segments

Reusing the same test for future objects
Object Representation How the sensor tests it
Road border One segment [C, D] One call to getIntersection
Traffic car Closed polygon of points Loop over consecutive point pairs
Wall or obstacle Polyline or polygon Same loop; open or closed
Collision between cars Two polygons Test every edge of one against every edge of the other

The nearest hit across all segments wins, so a car in front of the border hides the border, and a border in front of the car hides the car. No special case per object type is needed.

07Worked example

Ray from A = (320, 200) to B = (420, 200); border from C = (380, 0) to D = (380, 400).

08Common bugs

  • The fan does not turn with the car. Missing + this.car.angle after the lerp.
  • A one-ray sensor returns NaN. Missing the rayCount == 1 ? 0.5 guard; i / 0 is not a fraction.
  • The comment says 45°, the fan is 90°. Math.PI / 2 is 90°; Math.PI / 4 is 45°. Trust the arithmetic.
  • A ray hits an object that is not there. The infinite lines cross outside one of the segments; check both t and u bounds.
  • The nearest hit is the wrong one. Compare t (or t × length when lengths differ), not pixel x or y.
  • bottom is near zero, not zero. Nearly parallel lines give huge fractions; the bounds reject them. Exact parallel lines return null.
  • Traffic is ignored. #getReading only loops over the segments it is given. Add the polygon edges and pass the traffic array through.

A safe rewrite

Instead of comparing floats with ===, reduce the touches to the one with the smallest offset:

return touches.reduce((best, touch) => !best || touch.offset < best.offset ? touch : best, null);
